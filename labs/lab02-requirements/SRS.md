# 1 引言

## 1.1 目的

本文档规定《校园社团活动管理系统》的业务边界、功能需求、非功能需求、接口约束、业务规则与验收依据，供课程教师评审，并作为后续设计、实现和测试的输入。本文描述需求目标，不表示系统已经实现或测试通过。

## 1.2 背景

《校园社团活动管理系统》定位为面向学校社团管理中心、学生社团和普通学生的校园社团综合管理与协同平台。学校社团管理中心负责平台级业务管理、社团治理、活动审核、资源协调、统计和审计；各学生社团负责成员管理、活动组织、筹备协作、报名签到管理和资源申请；普通学生负责社团发现、入社申请、活动浏览、报名、签到、评价和个人记录。

课程实验中的模拟调研呈现了活动信息分散、报名状态不清、筹备责任不明确以及审核和签到难以追踪等问题。本项目拟建立覆盖“社团治理—活动筹备—审核发布—报名—签到—结束”的管理闭环，并通过权限、通知和审计约束关键操作。访客可作为浏览公开信息的辅助 Actor，但不构成独立业务层级。

模拟问卷共 20 条匿名响应，访谈覆盖普通学生、社团负责人和学校社团管理中心工作人员三类角色；这些材料只用于练习需求获取、分析和取舍，不能推断暨南大学实际用户需求。真实部署前仍需真实用户调研和学校规则确认。

## 1.6 需求描述约定

- FR-xxx 表示功能需求，NFR-xxx 表示非功能需求，BR-xxx 表示业务规则。
- 编号在项目生命周期内保持稳定。需求修改应记录原因与影响，不得为排版或版本变化随意更换已有 ID。
- 追踪以单个 FR、NFR、BR 为基本颗粒度，当前记录来源；后续补充 Design ID 和 Test Case ID。
- Must 是当前课程版本的最低业务闭环；Should 是时间允许时优先考虑的能力；Could 是核心范围稳定后的扩展；Won't 表示当前版本不纳入。
- TBD 表示参数尚未取得可靠依据，必须在相关设计或测试开始前确认并记录。
- 功能需求按“业务描述、适用用户、前置条件、输入、输出、正常流程、异常流程、业务规则、优先级、验收条件”描述。
- “应”表示可验证的要求；“可”表示允许的能力或条件，不表示已实现。

# 2 项目概述

## 2.1 系统功能

系统功能分为用户与权限、社团治理与成员、活动管理、报名与签到、筹备协作、资源管理、通知与待办、反馈统计与管理中心治理八组。完整结构见 `models/system-function-structure.md`，角色关系见 `models/use-case-model.md`。

系统围绕三层业务关系提供能力：学校社团管理中心执行跨社团审核、治理、资源审批、统计与审计；各学生社团管理本社团成员、活动、任务、报名签到和资源申请；普通学生管理自己的入社申请、活动参与、评价和个人记录。当前 Must 覆盖身份和归属授权、社团与入社、活动创建审核发布、浏览报名取消签到、筹备任务、关键站内通知、数据保护、备份恢复和运行日志；社团备案、状态和负责人变更作为 Should 纳入 requirements-v1.1 草案。

## 2.2 业务描述

1. 学生社团负责人提交社团备案信息；学校社团管理中心工作人员审核备案，管理社团正常、停用等业务状态，并确认负责人变更。
2. 普通学生浏览公开社团与活动，提交自己的入社申请，查看活动时间、地点、容量、报名截止时间和状态。
3. 社团负责人处理本社团入社申请，管理成员，创建活动草稿并提交审核；学校社团管理中心工作人员通过或驳回活动，驳回必须说明原因。
4. 通过审核的活动由所属社团负责人发布；Published 只表示公开可见，负责人另行开启报名后才进入 RegistrationOpen；若截止前未开启，到达截止时间后也进入 RegistrationClosed，以便后续按生命周期推进。
5. 普通学生只能在 RegistrationOpen 且当前时间早于报名截止时间时正式报名；容量、重复提交和候补按统一规则处理。
6. 普通学生可在报名截止时间前自行取消，超过截止时间不得自行取消；活动进行中由所属社团内获授权的成员为正式报名者签到。
7. 社团负责人分配筹备任务，社团成员按授权更新状态；关键业务变化通过站内通知告知对应用户。
8. 社团负责人提交场地和物资申请；学校社团管理中心工作人员负责跨社团资源审批和冲突协调，敏感操作留下可追踪记录。

## 2.3 数据流程描述

当前需求使用 Use Case 表达参与者与目标，使用业务流程表达活动和报名状态变化，使用概念 ER 模型表达实体关系。这三类模型已覆盖本阶段评审所需信息，因此不单独维护 DFD，避免对相同信息重复建模。若教师评审要求或后续出现跨系统复杂数据交换，再以变更记录补充 DFD。

核心业务流程见 `models/business-flow.md`，概念数据关系见 `models/domain-data-model.md`。

## 2.4 用户的特点

| 用户 | 特点与主要职责 |
|---|---|
| 访客 | 辅助 Actor；可浏览公开社团和活动信息，不执行受保护操作，不构成独立业务层级 |
| 普通学生 | 管理自己的入社申请、报名、取消、签到结果、评价和个人记录；不能管理他人业务记录 |
| 社团成员 | 本质上仍是学生用户；在具体社团上下文中获得附加权限，处理被分配的所属社团筹备任务 |
| 社团负责人 | 本质上仍是学生用户；只能管理自己负责社团范围内的成员、活动、报名签到、任务、资源申请和统计 |
| 学校社团管理中心工作人员 | 学校层面的业务管理角色；按职责拥有跨社团备案审核、活动审核、治理、资源审批、统计和审计权限，不表示技术运维权限 |

用户熟悉一般 Web 页面操作，但不能假定其了解活动状态机或技术术语，界面应提供明确的状态和错误反馈。

## 2.5 运行环境要求

系统预期通过桌面 Web Browser 访问。服务器、数据库、操作系统、浏览器版本、数据量、并发数和部署规模将在设计或测试计划中确定。目前尚无可运行的业务系统，性能与兼容性要求均为待验证目标。

## 2.6 设计和实现上的限制

- 课程项目由个人完成，应优先保证 Must 的完整性和可测试性。
- 当前没有学校统一身份、场地、邮件或消息平台的已确认接口；课程版本只承诺站内通知。
- 所有业务时间以系统统一时间判定，报名截止时间不晚于活动开始时间，活动开始时间早于结束时间。
- 权限检查同时考虑 Role Permission 与 Resource Ownership：普通学生只管理本人业务记录；社团负责人只管理自己负责的社团；管理中心工作人员按职责执行跨社团业务治理，不能仅依赖页面隐藏。
- 当前范围不包含财务系统、即时聊天、在线文档、视频会议、邮箱、支付、复杂行政审批、复杂 AI 推荐和社交媒体功能。
- 真实个人信息的采集应最小化；Public 仓库不得保存凭据或真实个人数据。

# 3 功能需求的描述

## 3.1 用户、权限与社团治理

| ID / 名称 | 业务描述与适用用户 | 前置条件与主要输入 | 主要输出与正常流程 | 异常/替代流程与关键规则 | Priority / 验收条件 |
|---|---|---|---|---|---|
| FR-001 身份认证 | 用户通过账号凭据建立登录状态 | 有效账号；输入账号与密码 | 校验凭据，成功后建立登录状态 | 凭据错误则拒绝，且不能访问受保护操作；受 NFR-004 约束 | Must；正确凭据可登录，错误凭据不可访问受保护操作 |
| FR-002 角色与归属授权 | 已登录用户访问受保护资源时同时校验角色和所属社团 | 已登录；输入目标资源与操作 | 权限与资源归属都满足时允许操作 | 任一条件不满足即拒绝；遵守 BR-009 | Must；其他社团负责人修改目标社团活动时被拒绝 |
| FR-003 社团信息浏览 | 用户查看社团名称、简介和公开活动 | 社团存在；输入社团标识 | 返回公开社团信息和公开活动 | 社团不存在时提示未找到；不展示内部成员信息 | Must；学生可查看公开信息，内部成员信息不可见 |
| FR-004 入社申请 | 普通学生申请加入指定社团 | 已登录且尚非该社团成员；输入社团与申请信息 | 创建待处理申请并返回状态 | 已是成员或已有有效待处理申请时拒绝 | Must；同一学生对同一社团最多一条有效待处理申请 |
| FR-005 入社处理与成员查看 | 所属社团负责人处理申请并查看成员 | 有待处理申请；输入通过或拒绝决定 | 记录决定；通过时建立成员关系 | 非所属负责人被拒绝 | Must；通过后申请者出现在成员名单，拒绝后不出现 |
| FR-032 成员身份维护 | 所属社团负责人调整本社团成员身份 | 已有成员；输入新身份或状态 | 更新成员身份并记录变更 | 不允许修改其他社团成员；遵守 BR-009 | Must；新权限生效，历史变更可追踪 |
| FR-033 社团备案与审核 | 学生社团负责人提交备案信息，学校社团管理中心工作人员审核 | 社团尚未完成有效备案；输入备案信息及审核决定 | 保存备案并进入待审；审核后记录通过或驳回，驳回须有原因 | 信息不完整、重复有效备案或无审核权限时拒绝 | Should；提交后可查看待审状态，通过后备案生效，驳回时可查看原因 |
| FR-034 社团状态及负责人变更管理 | 学校社团管理中心工作人员管理社团业务状态并确认负责人变更 | 社团已备案；输入状态调整或负责人变更信息 | 更新正常、停用等业务状态；记录负责人变更、确认人和时间 | 无治理权限、社团不存在或信息不完整时拒绝 | Should；新状态生效，负责人变更记录包含原负责人、新负责人、确认人和时间 |

FR-033、FR-034 来源于“项目范围澄清（2026-09-29）”，当前状态为待评审。

# 5 外部接口说明

## 5.1 用户界面

系统通过 Web Browser 提供列表、详情、表单、状态反馈和错误提示。不同角色只看到其有权访问的操作和字段；服务端仍须执行授权检查。状态名称面向普通用户时应配合易懂说明。

## 5.2 软件接口

当前没有已确认的学校统一身份、场地、邮件、短信或统一消息接口。站内通知属于当前范围。若后续接入外部系统，应通过变更流程补充身份认证方式、字段映射、失败处理、权限边界和验收条件。

## 5.3 通信接口

系统预期通过 Web 常用的安全传输方式访问，具体协议版本、证书和部署拓扑在设计阶段确定。任何网络通信都不得暴露密码、令牌或未授权个人信息。

## 5.4 数据交换接口

FR-030 允许在授权范围内导出活动统计，导出值应与当前统计一致且不包含联系方式。导出格式为 TBD，须在实现前确认。

# 6 其他需求

## 6.1 业务规则

BR-001～BR-012 是功能需求的共同约束，完整表见 `requirements/business-rules.md`。其中：

- BR-001：只有 RegistrationOpen 且当前时间早于报名截止时间时允许正式报名；Published 只表示公开可见。
- BR-004：学生可在报名截止时间前自行取消；超过截止时间不得自行取消。
- BR-006：活动状态依次由 Draft、Submitted、Approved/Rejected、Published、RegistrationOpen、RegistrationClosed、InProgress、Finished、Archived 演进，并允许开始前取消。
- BR-009：敏感操作同时检查 Role Permission 与 Resource Ownership；普通学生、社团负责人和管理中心工作人员分别受本人记录、所属社团和职责范围约束。

## 6.2 数据要求

核心实体包括用户、社团、社团备案、社团业务状态、负责人关系、成员关系、活动、审核、报名、签到、筹备任务、场地申请、通知、评价、举报和审计记录。概念关系与简要数据字典见 `models/domain-data-model.md`。本阶段不规定数据库表、字段类型、索引或存储产品。

## 6.3 范围与质量边界

MoSCoW 取舍见 `requirements/requirements-priority.md`。Should/Could 尚未承诺全部开发。模拟问卷支持率不等于需求已获真实用户确认，也不等于系统已经通过验收。

# 7 需求变更识别

教师发布正式 SRS 模板和相关课程资料属于外部约束变化，已记录为 CR-001。2026-09-29 对三层角色体系和产品定位的项目范围澄清已记录为 CR-002，并新增 FR-033、FR-034。两项变更详见 `../../docs/project-management/change-log.md`；CR-002 来源于课程项目范围确认 / 项目负责人确认，不表示教师已经批准。

后续需求变更按以下流程处理：

1. 记录变更请求、来源、原因和提出日期。
2. 分析对 FR/NFR/BR、优先级、模型、设计、实现、测试、进度和风险的影响。
3. 由课程教师或约定评审决定接受、拒绝或推迟；未取得决定时不得写成已批准。
4. 接受后修改相关工作产品，保留已有 ID；新增需求使用新的连续 ID。
5. 更新追踪矩阵、Backlog、版本记录和必要测试。
6. 完成验证与复核后，再按配置管理规则建立新基线；旧 Tag 保持不变。
