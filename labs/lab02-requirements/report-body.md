# 实验2报告正文 需求分析

## 一 实验目的与对象

本实验通过问卷调查分析校园社团活动管理系统的需求，完成需求获取、分析、规格化和追踪。系统面向普通学生、学生社团和学校社团管理中心，覆盖活动筹备、审核发布、报名签到与协作。本文说明调查结果、功能范围、业务规则和验收要求。

## 二 需求获取与数据确认

我将匿名问卷发布在微信群中，请各阶段学生自愿填写。原始回收时间为2026年10月20日至21日，共369份。对回答中的互斥选项冲突和经历不一致，由原填写者逐项确认后修订；本次正式统计使用修订版工作簿的“清洗后数据”。文件保留2600条修订记录，涉及353份答卷。369份均通过既定一致性检查，作为本次分析样本。

本次调查采用线上问卷和便利抽样。由于未采集完整的学校分布、邀请人数及未回应人数，结果仅描述本次受访学生，不计算总体回收率或学校总体比例。

## 三 问卷设计与样本

线上问卷共23题，包括年级和活动经历，以及活动渠道、信息相符程度、筛选、报名取消、候补提醒、签到、历史记录、成员管理、任务分工、资源申请、隐私与开放建议。线上题号Q01～Q23和最初Word题号的对应关系已整理到仓库。

年级分布为大一91人、大二79人、大三67人、大四56人、研究生43人、其他33人。参加过活动190人，有筹备或负责人经历187人，接触过场地物资申请243人，经历分组可能重叠。多选题各选项比例之和可超过100%；签到、筹备和资源困难分别使用190、187、243人的相关经历分母。

## 四 问卷主要结果

| 调查方向 | 结果 | 需求含义 |
|---|---|---|
| 报名步骤Q06 | 有报名经历331人中，填写信息106人（32.0%）、寻找入口80人（24.2%）、确认成功71人（21.5%） | 简化填写，突出入口和结果状态 |
| 满员偏好Q09 | 候补163/369（44.2%），为最大单项偏好但未过半 | 保留候补及顺位提示，考虑其他偏好 |
| 提醒Q10 | 报名结果200人、活动临近194人；无需提醒64人（17.3%） | 通知类型可选择，减少无关打扰 |
| 签到Q12 | 活动参与者中，记录不清楚93/190（48.9%） | 签到结果与本人记录可查 |
| 筹备Q18 | 截止93/187（49.7%）、负责人88/187（47.1%）、状态80/187（42.8%） | 任务明确责任、期限与进度 |
| 资源Q19 | 审批进度157/243（64.6%）、可用性139/243（57.2%）、冲突122/243（50.2%） | 展示申请状态和占用情况 |
| 信息相符Q04 | 可判断343人中相符129人（37.6%）、不相符137人（39.9%） | 提供统一活动入口和筛选；样本对信息分散感未形成多数共识 |

Q21中308/369（83.5%）选择至少一种信息应限制可见。开放题出现流程、信息通知、场地审批、移动界面、隐私等方向。开放题按关键词归类，统计各主题的提及次数，未区分赞成、反对或条件性意见。

## 五 功能需求与业务规则

功能需求编号为FR-001～FR-034，逐项记录参与者、条件、正常和异常结果、优先级、验收标准与来源。核心功能为身份与归属授权、社团信息和入社、活动草稿与审核发布、活动筛选和详情、报名取消与容量控制、签到、筹备任务及关键通知。

| 功能组 | 需求编号 | 主要验收条件 |
|---|---|---|
| 身份和社团 | FR-001～FR-005、FR-032～FR-034 | 登录后核对角色与社团归属；重复申请被拒绝；成员状态变更留痕 |
| 活动管理 | FR-006～FR-011 | 草稿不公开；未审核通过不能发布；筛选仅返回公开匹配活动 |
| 报名签到 | FR-012～FR-017 | 同人同活动不重复报名；不超容量；按条件取消和候补；签到唯一 |
| 筹备通知 | FR-018～FR-023 | 任务有负责人、期限和状态；更新及通知仅向有权限者展示 |
| 资源反馈 | FR-024～FR-031 | 资源状态可查；冲突拒绝批准；评价和统计与本人或所属社团关联 |

业务规则编号BR-001～BR-012，约束活动状态、报名截止、候补顺序、签到资格、任务字段和资源冲突。问卷反映使用问题和偏好；审核制度、精确截止边界和完整权限矩阵属于项目设计约束，相关校方制度尚待核实。

## 六 非功能需求

NFR-001～NFR-014涵盖易用性、性能、可靠性、身份与会话安全、审计、可维护性、可测试性、兼容性、完整性、隐私、备份和日志。验收方式包括越权请求应拒绝、重复操作不产生重复业务记录、统计与原记录一致、敏感信息按职责展示、备份可恢复。性能负载、响应阈值、浏览器清单和日志保留期须在相应测试前明确，并由系统测试验证。

## 七 需求优先级与规格说明

Must涵盖身份、社团、活动、报名签到、筹备任务和关键通知等基本功能。候补、个人记录、日历看板、场地和治理等保留Should；物资、简单推荐、举报、导出和审计查看保留Could。资源功能的安排结合调查需求、实施依赖和课程工作量确定。即时聊天、办公套件、支付和复杂社交功能不进入本期范围。

软件需求规格说明书版本为requirements-v1.2，包含调查结果、功能需求、非功能需求、业务规则及相关模型。需求来源对应具体题目、频数和统计脚本，项目设计约束另行标注。Must、Should和Could表示需求优先级，当前实现状态由开发分支和追踪矩阵记录。

## 八 实验结果与后续工作

本次形成369份修订后问卷的正式统计、23题映射、34项功能需求、14项非功能需求、12项业务规则及更新后的SRS和追踪矩阵。统计脚本输出汇总CSV与JSON，公开仓库不保存IP或逐人原文，原始工作簿和修订记录留在本地。

通过本次实验，我将问卷反馈整理为可追踪的需求，并为各项比例明确了分母。后续设计和测试将依据需求编号验证权限、状态变化和异常处理；学校相关制度仍需在正式部署前核实。
