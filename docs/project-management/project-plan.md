# 项目计划

## 1 项目目标

完成《校园社团活动管理系统》课程项目，将其建设为面向学校社团管理中心、学生社团和普通学生的校园社团综合管理与协同平台。以可追踪的需求为基础，逐步交付用户权限、社团治理、活动审核发布、报名签到、筹备协作和必要治理能力，并形成与课程实验相匹配的文档、代码和测试成果。

## 2 项目范围

当前范围以 SRS 的 Must 为核心，Should 和 Could 依据进度与评审结果选取。学校社团管理中心负责跨社团审核、治理、资源审批、统计与审计；各学生社团负责本社团成员、活动、筹备、报名签到和资源申请；普通学生管理自己的入社申请、报名、签到、评价和个人记录。访客仅浏览公开信息。系统边界不含即时聊天、在线文档、视频会议、邮箱、支付、财务系统、复杂行政审批、复杂 AI 推荐和社交媒体平台。

## 3 开发方式

本课程项目由个人完成，采用轻量化迭代开发方式，借鉴 Scrum 的 Product Backlog、优先级、迭代规划和增量交付。项目不机械模拟多人 Scrum 组织，也不编造会议或客户确认记录。当前没有历史 Velocity，工作量估计仅用于相对比较和排期，执行后再根据真实进度调整。

## 4 工作分解结构（WBS）

| WBS | 工作包 | 主要内容 |
|---|---|---|
| 1 | 课程与环境基础 | 仓库、工具链、环境审计、提交规范 |
| 2 | 需求工程 | 模拟调研、SRS、FR/NFR/BR、模型、追踪与变更控制 |
| 3 | 总体与详细设计 | 架构、模块、数据、接口和安全设计 |
| 4 | 核心实现 | 用户权限、社团治理、活动、审核、报名和容量控制 |
| 5 | 协作与扩展实现 | 签到、通知、任务及经确认的 Should/Could |
| 6 | 验证与发布 | 单元/集成/验收测试、缺陷修复、部署与总结 |

## 6 工作量估计

工作量先以 Story Points（SP）表达相对复杂度，1/2/3/5/8 分别表示从小到大的不确定性和投入。Product Backlog 的 SP 不是工时承诺；在没有历史 Velocity 前，不根据 SP 声称固定完成速度。每次迭代开始前根据课程时间、依赖和上一迭代实际结果重新核对范围。

## 7 阶段完成判据

- 需求阶段：教师模板章节齐全；FR/NFR/BR 编号连续且可追踪；关键规则一致；模拟调研属性明确；变更已记录并通过课程评审后再建立新基线。
- 设计阶段：每个 Must FR 有对应设计；接口、数据、权限和异常处理可落实；关键设计决策可追踪。
- 实现阶段：目标 Backlog 条目满足验收条件；代码可构建并通过相关测试；文档和追踪同步更新。
- 发布阶段：Must 主流程通过约定测试；未解决问题有记录；提交物清单完整。

## 8 Definition of Done

一个 Backlog 条目只有同时满足以下条件才可标记为 DONE：

1. 关联需求与验收条件明确，范围变更已记录。
2. 实现经过自查，未引入与既有业务规则冲突的行为。
3. 必要的自动或手工测试已执行并留下可核对结果。
4. 权限、异常和数据一致性场景已覆盖。
5. 相关 SRS、设计、使用说明和追踪关系已同步。
6. 工作区不存在无关文件或公开敏感信息。

## 9 配置管理方式

- `main` 保存已评审的稳定版本，功能与文档变更在主题分支完成。
- 课程阶段基线使用带说明的 Git Tag；已有基线不得移动或重建。
- 合并前检查差异、状态、测试和敏感信息；禁止用 force push 覆盖共享历史。
- FR/NFR/BR ID 在项目生命周期内保持稳定；变更通过 CR 编号记录原因、影响和状态。
- 仓库为 Public，提交前应排除邮箱、凭据、令牌、真实个人数据和工具临时文件。
